## 1. 작업의 흐름

점검은 CLAUDE.md에 적힌 iCloud 전략과 실제 코드를 대조하는 것으로 시작했습니다. 크게 두 갈래의 문제가 나왔습니다.

**갈래 A — CloudKit을 켜면서 생긴 문제**
`NSPersistentCloudKitContainer`로 바꾸면서 CoreData의 모든 필드가 다른 기기로 복제되기 시작했습니다. 그런데 그 안에는 **기기 전용 데이터**(북마크)와 **CloudKit 제약을 어기는 데이터**(1MB 넘는 썸네일)가 섞여 있었습니다.

**갈래 B — 원래 있었지만 iCloud 때문에 드러난 문제**
로컬 파일만 다룰 땐 문제가 없던 코드들이, 파일이 클라우드에 있게 되면서 깨지기 시작했습니다. "파일이 있는데 내용은 없는" 상태를 아무도 고려하지 않고 있었습니다.

작업은 **위험도 순이 아니라 의존 순서**로 진행했습니다:

```
1단계  데이터를 파괴할 수 있는 코드부터 제거      (안전망 확보)
2단계  모델 4.2 — 필드 추가                      (스키마만 먼저)
3단계  경로 해석을 한 곳으로 모으기               (19곳 전환)
4단계  기존 논문에 새 필드 채우기 (백필)
5단계  마이그레이션이 새 필드를 관리하도록
```

각 단계가 끝날 때마다 앱이 정상 동작하는 상태를 유지했고, **매 단계마다 "기존 4.0 사용자가 업데이트하는 상황"을 시뮬레이터에서 재현해 데이터가 남는지 확인**했습니다.

## 2. 가장 큰 문제 — 북마크는 그 기기에서만 통합니다

### 무엇이 문제였나

`PaperData.url`에는 파일 경로 문자열이 아니라 **Security-scoped Bookmark**가 들어 있습니다. 그 안에는 이런 게 담깁니다:

- 이 기기의 볼륨(디스크) UUID
- 파일의 inode 번호
- `/var/mobile/Containers/Data/Application/A1B2C3.../Documents/논문.pdf`

즉 **"우리 집 냉장고 두 번째 칸"** 같은, 그 집 안에서만 통하는 표현입니다.

CloudKit은 이 필드를 그대로 다른 기기로 복제합니다:

```
[아이패드]                         [맥]
title: "논문.pdf"     ──────▶  title: "논문.pdf"      ✅
thumbnail: <이미지>   ──────▶  thumbnail: <이미지>     ✅
url: <아이패드 좌표>  ──────▶  url: <아이패드 좌표>    ❌ 맥에선 무의미
```

**사용자가 겪는 증상:** 맥에서 앱을 켜면 논문 목록이 제목·썸네일까지 멀쩡히 보입니다. 그런데 탭하면 안 열립니다. 파일은 iCloud Drive에 있는데 앱이 가는 길을 모르는 상태입니다.

### 어떻게 고쳤나

**저장소 기준 상대 경로**를 추가했습니다. 기기마다 다른 앞부분은 각자 조립하고, 뒷부분만 공유합니다.

```swift
// 저장: 기기마다 다른 앞부분은 빼고
relativePath = "논문.pdf"

// 열기: 각 기기가 자기 저장소 기준으로 조립
FileManager.default.pdfStorageDirectory.appending(path: relativePath)
```

경로를 찾는 코드가 **19곳에 흩어져 있어서** `PaperFileLocator` 하나로 모았습니다. 3단계로 내려갑니다:

| 순서 | 방법 | 언제 성공하나 |
|---|---|---|
| 1 | `저장소 / relativePath` | 정상 상태. **다른 기기에서도 여기서 성공** |
| 2 | 북마크 resolve | 백필 전이거나 파일이 저장소 밖에 있을 때 |
| 3 | `제목 + ".pdf"` 탐색 | 북마크까지 깨졌을 때의 마지막 복구 |

2·3단계로 찾아내면 알아낸 경로를 돌려줘서, 호출부가 기록해 두면 다음부터는 1단계에서 바로 잡힙니다(**자가 치유**).

> **이 폴백 구조가 안전성의 핵심입니다.** 백필이 실패하거나 아예 안 돌아도 2단계가 받쳐주기 때문에, 기존 사용자는 지금까지와 똑같이 동작합니다. 새 필드는 순수하게 이득만 얹는 구조입니다.

## 3. 기존 코드에 있던 문제들

iCloud 때문에 생긴 게 아니라, **원래 있었는데 iCloud가 방아쇠를 당긴** 것들입니다.

### 3-1. `resetContainer()` — 아무도 안 부르는 데이터 파괴 함수

```swift
public func resetContainer() {
    try coordinator.destroyPersistentStore(at: storeURL, ...)  // 전부 삭제
}
```

호출부가 하나도 없었습니다. 그런데 남아 있으면 언젠가 누가 "동기화 꼬였으니 리셋하지" 하고 부르게 됩니다. **삭제했습니다.**

### 3-2. `fatalError` — 마이그레이션 실패 = 앱 실행 불가

```swift
loadPersistentStores { _, error in
    if let error { fatalError(...) }   // 앱이 켜지지도 않음
}
```

마이그레이션이 실패하면 사용자는 **앱을 실행조차 못 하고, 스스로 복구할 방법도 없습니다.** 데이터가 날아간 것과 구분이 안 됩니다.

이제는 CloudKit 없이 한 번 더 시도해서 최소한 로컬 데이터는 열어 주고, 그것도 실패하면 `storeLoadFailure`에 담아 둡니다(앱은 죽지 않음). **어떤 실패 경로에서도 데이터를 지우는 처리는 하지 않습니다.**

### 3-3. `paperInfo!` — 강제 언래핑 2곳

원인은 `PDFSharedData.makeDocument`였습니다:

```swift
do {
    let url = try URL(resolvingBookmarkData: paperInfo.url, ...)  // 여기서 throw되면
    ...
    self.paperInfo = paperInfo        // 여기까지 도달 못 함 → nil로 남음
} catch {
    log("Failed to make Document")    // 로그만 찍고 끝
}
```

그런데 `NavigationCoordinator`는 실패해도 **화면을 그대로 엽니다.** 그 상태에서 figure 추출이 돌면 `paperInfo!` → 크래시.

즉 2장의 "다른 기기 북마크" 문제가 터지는 순간, 증상은 빈 화면이 아니라 **앱 크래시**였습니다.

**고친 방법:** `makeDocument`가 파일을 못 찾아도 `paperInfo`는 반드시 채우도록 바꿨습니다(`document`만 nil). 그리고 `!`를 쓰던 두 곳은 `guard let`을 한 줄 늘리고 **이미 있던 `else` 블록을 재사용**했습니다.

> `!`만 지우면 빌드가 깨집니다. `!`는 오류를 해결한 게 아니라 **컴파일 타임 오류를 런타임 크래시로 옮긴 것**이라, nil일 때 뭘 할지를 정해줘야 진짜로 해결됩니다.

### 3-4. CoreData를 백그라운드에서 만지던 문제

```swift
@MainActor func syncICloudStorage() async {
    try await migrationUseCase.migrate(...)   // ← 여기서 메인을 벗어남
}
```

`@MainActor` 함수가 `nonisolated async` 함수를 `await`하면 **호출된 함수는 메인 스레드를 떠납니다.** `@MainActor`는 전염되지 않습니다. 그래서 마이그레이션 중 모든 CoreData 접근이 메인 전용 `viewContext`를 백그라운드에서 건드리고 있었습니다.

대부분은 그냥 잘 돌아가서 더 위험합니다. 하필 마이그레이션 중이라 깨지면 파일 위치 정보가 날아갑니다.

**고친 방법:** 전용 백그라운드 컨텍스트 + `performAndWait`.

**확인 방법:** 스킴 인자에 `-com.apple.CoreData.ConcurrencyDebug 1`을 넣으면 위반 시 즉시 크래시하며 잡아줍니다.

### 3-5. 모델은 optional인데 Swift는 non-optional

커밋 `418b285`에서 `PaperTag`의 관계를 optional로 바꿨는데(CloudKit 필수 요건), **Swift 프로퍼티는 그대로였습니다.**

CloudKit은 레코드를 하나씩 따로 보냅니다:

```
1초차: PaperTag 도착   → paperData: nil,  tagData: nil
3초차: PaperData 도착  → paperData: 논문A, tagData: nil
5초차: TagData 도착    → paperData: 논문A, tagData: 태그
```

이 사이에 홈 화면이 그려지면 `paperTag.tagData.id`에서 크래시합니다. **새 기기에서 앱을 처음 켤 때만 죽는** 재현 어려운 버그가 됩니다.

**고친 방법:** 프로퍼티를 optional로 맞추고, 읽는 3곳을 `compactMap`으로 바꿔 아직 안 온 관계는 건너뜁니다. 동기화가 끝나면 `automaticallyMergesChangesFromParent`로 자동 반영됩니다.

### 3-6. 삭제할 때 파일을 통째로 읽던 코드

```swift
if let url = ...,
   let _ = try? Data(contentsOf: url) {      // 존재 확인하려고 PDF 전체를 메모리로
    try FileManager.default.removeItem(at: url)
}
```

두 가지 문제:
- iCloud에서 내용이 비워진 파일(placeholder)은 읽기가 실패 → **삭제를 건너뜀** → 앱에선 사라졌는데 iCloud엔 남는 고아 파일
- 50MB 논문을 지우려고 50MB를 메모리에 읽음

**고친 방법:** `try? removeItem`만 호출. 없으면 조용히 실패하는 걸로 충분합니다.

### 3-7. 파일 조정 없이 PDF 덮어쓰기

논문을 닫을 때마다(`onDisappear`) 필기가 반영된 PDF 전체를 원본에 덮어씁니다. iCloud Drive에서는 동기화 데몬이 동시에 그 파일을 만질 수 있는데, 조정 없이 쓰면 **업로드 도중 갈아엎어 파일이 깨질 수 있습니다.**

이 앱은 **필기가 PDF 파일 자체에 저장**되므로(별도 엔티티 없음) 파일이 깨지면 그 논문의 작업 내용 전체가 사라집니다.

**고친 방법:** `NSFileCoordinator`로 감쌌습니다.

> 이건 **파일이 깨지는 것만** 막습니다. 두 기기에서 동시에 필기하면 여전히 나중에 닫은 쪽이 이깁니다. 진짜 충돌 처리는 `NSFilePresenter`가 필요한 별개 범위입니다.

### 3-8. 썸네일이 CloudKit 레코드 한도를 넘을 수 있던 문제

썸네일을 **페이지 원본 크기 그대로, 무압축 PNG**로 저장하고 있었습니다. 크기 상한이 없었습니다.

실측(샘플 논문 2개): **212KB / 168KB**. CloudKit 레코드 한도는 약 1MB이고, 초과하면 그 레코드는 **업로드 자체가 실패**합니다. 앱에는 아무 에러도 안 뜹니다.

→ **"어떤 논문은 동기화되고 어떤 논문은 안 되는데 이유를 모르겠다"** 형태의 버그가 됩니다.

**고친 방법 (두 가지):**

1. **생성 시 제한** — 긴 변 600pt + JPEG 0.8 (홈 셀은 82×110pt라 지금 해상도는 과했습니다)
   - 212KB → **25KB** (8.4배)
   - 168KB → **75KB** (2.3배)
2. **모델에 External Storage 적용** — 앞으로 쓰이는 큰 데이터가 DB 행 밖으로 빠지면서 CloudKit이 CKAsset으로 취급 → 1MB 한도를 우회

> ⚠️ **External Storage는 기존 데이터에 소급 적용되지 않습니다.**
> 실측으로 확인했습니다 — 설정을 켠 뒤 4.0 → 4.2 마이그레이션을 돌리면
> `_EXTERNAL_DATA` 디렉터리는 만들어지지만 **비어 있고**, 212KB 썸네일은 행 안에 그대로 남습니다.
> Core Data는 값을 *새로 쓸 때* 크기를 보고 판단하는데, lightweight migration은 기존 값을 이월만 하기 때문입니다.
>
> 따라서 1·2번만으로는 **기존 사용자가 이미 가진 큰 썸네일이 그대로 남습니다.**
> 1번은 새로 추가되는 논문에만, 2번은 새로 쓰이는 값에만 적용되기 때문입니다.

3. **기존 썸네일 재생성 백필** (`PaperThumbnailBackfillUseCase`) — 위 빈틈을 메웁니다.
   실행 시 **300KB를 넘는 썸네일만** 골라 PDF 첫 페이지에서 다시 만들어 저장합니다.

   - **임계값이 300KB인 이유:** 재생성 결과(25~250KB)가 절대 임계값을 넘지 않아야
     **매 실행마다 무한 재처리되는 일이 없습니다.** 100KB처럼 낮게 잡으면 빽빽한 논문이
     재생성 후에도 임계값을 넘어 영원히 반복될 수 있습니다.
   - 파일을 읽을 수 없으면(아직 내려받지 않은 iCloud 파일 등) 건너뛰고 다음 실행에서 다시 시도합니다.
   - 실패해도 기존 썸네일이 그대로 남으므로 목록이 비어 보이지 않습니다.
   - 썸네일을 한꺼번에 메모리에 올리지 않도록, 크기 확인 후 곧바로 폴트로 되돌립니다.

**실측 검증** — 4.0 사용자가 900KB 썸네일(CloudKit 한도에 육박)을 가진 상태를 재현해 업그레이드:

```
업그레이드 전:  Reazy Sample Paper → 900,000B
업그레이드 후:  Reazy Sample Paper →  74,772B   (12배 축소, 유효한 JPEG)
로그:          "썸네일 백필: 1건 재생성, 0건 보류"

임계값 미만이던 212KB 논문 → 그대로 유지 (불필요한 재처리 없음)
재실행 → 아무것도 안 함 (멱등)
url 북마크 → 바이트 동일
```

## 4. 마이그레이션 안전성 — 어떻게 확인했나

"필드를 추가하다 데이터가 날아가지 않을까"가 가장 큰 우려였습니다. 말로 안심시키는 대신 **실제 프로덕션 경로를 재현해서 측정**했습니다.

### 방법


> **주의할 관찰 하나:** External Storage를 켜면 SQLite의 썸네일 BLOB이 **1바이트 늘어납니다**(예: 212361 → 212362). Core Data가 저장 모드를 표시하려고 붙이는 마커이고, 그 뒤에 PNG 시그니처(`89504E47`)가 그대로 이어집니다. **데이터 손실이 아니라 인코딩 변화입니다.** 마커를 뗀 실제 이미지 바이트는 완전히 동일한 것을 확인했습니다.

### 왜 안전한가

Core Data의 lightweight migration은 새 컬럼을 `NULL`로 추가할 뿐 **기존 행을 건드리지 않습니다.** 특히 관계가 바뀐 4.1 단계를 **4.0 → 4.2로 건너뛰어도** 태그 연결이 그대로 살아남는 것을 확인했습니다. 여기가 가장 위험했던 지점입니다.

### 설계에 넣은 안전 원칙

| 원칙 | 의미 |
|---|---|
| **파일을 옮기지 않는다** | 백필은 CoreData 필드만 씁니다. 파일 I/O가 없습니다 |
| **필드를 지우지 않는다** | 기존 북마크는 영구 보존. 새 필드는 *추가만* |
| **되돌릴 수 있다** | 백필이 틀려도 북마크가 그대로라 이전 동작으로 복귀 가능 |
| **부분 실패해도 안전** | 안 채워진 논문은 북마크 폴백으로 계속 동작 |

백필은 전용 `updateRelativePaths`를 써서 **북마크는 아예 건드릴 수 없게** 했습니다. 검증에서도 북마크가 바이트 단위로 동일함을 확인했습니다.

## 5. 작업 중 마주친 문제와 해결

기록 삼아 남깁니다.

**① `!`만 지우면 빌드가 깨진다**
→ 맞습니다. `!`는 컴파일 오류를 런타임 크래시로 옮긴 것이라, nil일 때의 동작을 정해줘야 합니다. 다행히 두 곳 다 `guard` 안이라 처리할 `else`가 이미 있었습니다.

**② "원장 기반 재개"가 설계대로 안 됐다**
설계 때 마이그레이션 재개 판정을 원장으로 바꾸겠다고 했는데, 코드를 보니 **원장에는 완료된 논문만 기록**됩니다. 복사 도중 죽은 논문은 원장에 아무것도 없어서 원장으로는 해결이 안 됐습니다.
→ 대신 **크기 + 앞 64KB 내용 비교**로 바꿨습니다. "이름도 같고 크기도 우연히 같은 남의 파일"을 내 논문으로 연결하는 사고를 막으면서, 전체를 읽지 않아 iCloud에서 통째로 내려받지도 않습니다.

**③ 검증 중 비교 오류**
북마크 해시가 달라졌길래 데이터 변조인 줄 알았는데, **앱을 새로 설치할 때마다 컨테이너 UUID가 바뀌어** 북마크도 달라지는 것이었습니다. 다른 설치 세션의 값과 비교한 제 실수였습니다. 같은 설치 기준으로 다시 재니 완전히 동일했습니다.

**④ 커밋 컨벤션**
처음 두 커밋에 긴 본문을 붙였는데, 팀 히스토리를 보니 최근 12개가 전부 본문 없는 한 줄이었습니다. 로컬 커밋이라 재작성했습니다.

**⑤ SourceKit 허위 오류**
편집 중 "Cannot find type ... in scope" 같은 오류가 여러 번 떴지만 전부 인덱스가 안 잡혀서 난 허위였습니다. 실제 빌드는 통과했습니다. 다만 그중 **파라미터가 함수를 가리는 진짜 오류**가 하나 섞여 있었으므로(`relativePath`), 전부 무시하지 말고 확인이 필요합니다.

## 6. 아직 남은 작업 — 디자인이 필요한 것들

세 건 모두 **"iCloud가 뜻대로 안 될 때 무엇을 보여줄 것인가"** 라는 하나의 주제입니다. 현재 앱에는 이 상황을 표현할 UI가 **하나도 없습니다.** 함께 의뢰하는 것을 권합니다.

### ① 클라우드에만 있는 논문 (2번)

**왜 필요한가**
iCloud Drive는 항상 전체 복사본을 갖고 있지 않습니다. 기기 저장 공간이 부족해지면 iOS가 알아서 파일 내용을 지우고 껍데기만 남깁니다(placeholder). **경로는 그대로 있고 `fileExists`도 true라서** 겉보기엔 파일이 있는 것처럼 보이지만, 열면 실패합니다.

사용자가 한 일은 없는데 어느 날 갑자기 이 상태가 됩니다. → **"어제는 됐는데 오늘은 안 돼요"**

**필요한 디자인**

1. **홈 셀의 "클라우드에만 있음" 표시** — 탭하기 전에 알 수 있어야 합니다. 파일 앱의 ☁️ 배지 역할. 기존 셀(썸네일 + 제목 + 날짜 + 태그 칩) 어디에 넣을지 결정 필요
2. **다운로드 진행 상태** — 논문 하나가 수십 MB라 즉시 안 열립니다. 진행률과 취소 수단 필요. 셀 안에서 할지 전체 오버레이로 갈지 결정 필요
3. **다운로드 실패 상태** — 오프라인이거나 파일이 사라진 경우. 재시도 포함

**연관된 회귀 하나**
`navigateToPaper`가 이제 파일 존재까지 확인합니다. 예전엔 빈 PDF 화면이 열렸는데 지금은 **아무 반응이 없습니다.** 파일이 정상인 사용자에겐 차이가 없지만, "탭해도 반응 없음"은 좋은 UX가 아닙니다. 이 디자인에서 함께 해결되어야 합니다.

### ② 중단된 이동 재개 (5번)

**왜 필요한가**
파일을 옮기는 도중 앱이 죽으면 절반은 옮겨지고 절반은 그대로인 상태가 됩니다. 지금은 **iCloud가 켜져 있을 때만** 자동 재시도하므로, 켜는 도중 중단되면(플래그는 아직 꺼짐) 자동 재개도 롤백도 안 걸립니다.

**먼저 정해야 할 것 — 디자인 이전에 정책입니다**

- **A안: 조용히 자동 재개** — 방해하지 않음. 대신 왜 앱이 느린지 모름
- **B안: 물어보고 재개** — "이전에 완료되지 못한 iCloud 이동이 있습니다. 계속할까요?" / [계속] [나중에]

**필요한 디자인**
A안이면 상단 배너형 진행 표시, B안이면 실행 시 alert + 진행 표시. 어느 쪽이든 **"지금 파일을 옮기는 중"임을 알리는 표시**는 필요합니다. 수백 MB 이동에는 시간이 걸립니다.

### ③ 실패 상태 표현 (6번)

**왜 필요한가**
지금은 iCloud를 켜려다 실패해도 **아무것도 안 보이고** 토글만 원위치로 돌아갑니다. 사용자는 자기가 잘못 눌렀다고 생각합니다.

**필요한 디자인 — 원인별로 할 수 있는 행동이 달라 문구도 달라야 합니다**

| 원인 | 사용자가 해야 할 일 |
|---|---|
| iCloud 미로그인 | 기기 설정에서 로그인 (설정 앱으로 보내는 버튼이 있으면 좋음) |
| 저장 공간 부족 | 용량 정리 또는 업그레이드 |
| 네트워크 없음 | 연결되면 자동 재시도됨을 안내 (재시도 로직은 이미 구현됨) |
| 원인 불명 | 재시도 버튼 |

**두 군데에 필요합니다**
1. **즉시 알림** — 토글을 눌렀는데 실패한 직후 (alert 또는 토스트)
2. **iCloud 설정 화면의 지속 상태** — 현재는 "마지막 동기화: N분 전" 한 줄뿐. 실패 중일 때는 그 자리에 상태와 재시도 수단이 필요

> 코드 쪽 준비는 되어 있습니다. `PersistantContainer.isCloudKitEnabled` / `storeLoadFailure`로 상태를 읽을 수 있습니다.

### ④ 함께 넘기면 좋은 것

- **이동 진행률 UI** — `iCloudMigrationProgress(완료 수, 전체 수)`가 **이미 계산되어 있는데 화면에서 안 쓰입니다.** 지금은 "동기화 중" 텍스트만 나옵니다
- **시스템 alert → 커스텀 alert 통일** — iCloud 설정의 "끄기" 확인만 iOS 기본 alert이라, 온보딩 alert이나 논문 삭제 alert과 생김새가 다릅니다

## 7. 출시 전 체크리스트

### 🔴 반드시 해야 하는 운영 작업 — CloudKit 스키마 배포

**이걸 빠뜨리고 출시하면 프로덕션 사용자의 동기화가 조용히 멈춥니다.** 앱은 정상 실행되고 에러도 안 뜨는데 기기 간에 아무것도 안 넘어갑니다.

#### 왜 필요한가

CloudKit에는 환경이 **두 개** 있습니다.

| 환경 | 누가 쓰나 |
|---|---|
| **Development** | Xcode에서 직접 빌드해 설치한 앱 |
| **Production** | TestFlight · App Store로 배포된 앱 |

`NSPersistentCloudKitContainer`는 CoreData 모델을 보고 CloudKit 스키마(레코드 타입·필드)를 **자동 생성해 주는데, Development 환경에서만** 합니다. Production 환경에는 **사람이 직접 배포**해야 합니다.

즉 개발 중에는 잘 되다가 TestFlight에 올리는 순간 동기화가 멈추는 형태로 터집니다.

#### 1단계 — Development 스키마 채우기

배포하려면 Development 쪽에 스키마가 먼저 만들어져 있어야 합니다. 두 가지 방법이 있습니다.

**방법 A: 앱을 실제로 돌려서 채우기 (간단하지만 누락 위험)**

iCloud에 로그인된 실기기에 Xcode로 빌드해 설치하고, **모든 종류의 데이터를 한 번씩 만들어 봅니다** — 논문 추가, 태그 달기, 폴더 만들기, 코멘트 쓰기, figure 저장 등.

한 번도 안 만들어 본 레코드 타입은 스키마에 안 생깁니다. **어떤 엔티티는 동기화되고 어떤 건 안 되는** 상태가 되기 쉬워서 권장하지 않습니다.

**방법 B: `initializeCloudKitSchema`로 한 번에 생성 (권장)**

모델 전체를 훑어 스키마를 만들어 줍니다. 누락이 없습니다.

```swift
// PersistantContainer의 init 안, loadPersistentStores 직후에 임시로 추가
#if DEBUG
do {
    try self._container.initializeCloudKitSchema(options: [])
    log("CloudKit 스키마 생성 완료")
} catch {
    log("CloudKit 스키마 생성 실패: \(error)")
}
#endif
```

주의할 점:

- **개발용으로 한 번만 돌리고 반드시 지우거나 주석 처리하세요.** 매 실행마다 돌리면 느려집니다
- 내부적으로 **더미 레코드를 만들었다가 지웁니다.** 실제 사용자 데이터에는 영향이 없지만, 개발용 iCloud 계정으로 돌리세요
- 실기기 + iCloud 로그인 상태가 필요합니다 (시뮬레이터는 계정이 없으면 안 됩니다)
- 몇 분 걸릴 수 있습니다

#### 2단계 — Console에서 확인

1. [CloudKit Console](https://icloud.developer.apple.com/dashboard) 접속 (Apple Developer 계정 로그인)
2. 컨테이너 **`iCloud.com.chillin.reazy`** 선택
3. 좌측 **Schema → Record Types**
4. 이번 작업으로 추가된 필드가 있는지 확인:

| 확인할 것 | 있어야 하는 필드 |
|---|---|
| `CD_PaperData` | `CD_relativePath`, `CD_focusRelativePath` |

> Core Data가 만드는 레코드 타입·필드에는 **`CD_` 접두사**가 붙습니다. 엔티티 `PaperData` → 레코드 타입 `CD_PaperData`, 속성 `relativePath` → 필드 `CD_relativePath`.

이 두 필드가 안 보이면 1단계가 제대로 안 된 것입니다. **없는 상태로 배포하면 안 됩니다.**

#### 3단계 — Production으로 배포

1. 같은 Console에서 좌측 **Schema** 화면 우측 상단의 **`Deploy Schema Changes...`** 버튼 클릭
2. Development ↔ Production 차이가 목록으로 나옵니다 — **추가되는 레코드 타입·필드를 눈으로 확인**
3. 확인 후 배포

배포는 보통 수 초~수 분이면 끝납니다.

#### ⚠️ 배포 전 반드시 알아야 할 것

**되돌릴 수 없습니다.** CloudKit은 Production에 한 번 올라간 **레코드 타입과 필드를 삭제할 수 없습니다.** 이름을 바꾸는 것도 안 됩니다.

이번에 `relativePath` / `focusRelativePath`라는 이름이 **영구 확정**됩니다. 배포 전에 이름이 마음에 드는지 한 번 더 확인하세요.

**앞으로 모델을 바꿀 때마다 이 절차를 반복해야 합니다.** CoreData 모델에 필드를 추가하는 것만으로는 Production에 반영되지 않습니다. 새 버전을 출시할 때 체크리스트에 넣어 두세요.

**배포 순서:** 스키마를 **먼저** 배포하고 앱을 출시하세요. 반대로 하면 그 사이에 업데이트한 사용자의 동기화가 실패합니다.

#### 배포 후 확인

- [ ] TestFlight 빌드를 기기 2대에 설치
- [ ] 한쪽에서 논문 추가 → 다른 쪽에 나타나는지
- [ ] 그 논문이 **열리는지** (2장의 `relativePath`가 실제로 넘어갔는지 확인하는 지점)

### 🟡 실기기 검증이 필요한 것

시뮬레이터에 iCloud 계정이 없어 아래는 확인하지 못했습니다.

- [ ] **기기 2대 동기화** — 아이패드에서 추가한 논문이 맥에서 열리는지 (2장의 핵심)
- [ ] **논문 열기 / figure 추출** — 3단계에서 19곳을 바꿨는데, 실제로 여는 경로는 `simctl`로 탭을 못 해서 미검증
- [ ] **파일 앱에 `Reazy` 폴더 노출** (8번)
- [ ] **백그라운드 동기화** — 두 기기를 켜둔 채 한쪽에서 추가 시 재시작 없이 반영되는지 (9번)
- [ ] **iCloud 끄기** — 설정에서 토글 OFF. 이때 `-com.apple.CoreData.ConcurrencyDebug 1`을 켜두면 3-4의 스레드 위반이 재발했는지 함께 잡힙니다
- [ ] **필기 보존** — 필기 후 닫았다 다시 열기 (3-7)

### 🟡 현지화(영어·일본어) 추가 필요 — 다른 개발자 담당

이 앱은 **한국어(원본) + 영어 + 일본어**를 지원합니다. iCloud UI를 만들 때 Swift 코드만 들어가고
`Localizable.xcstrings` 갱신이 빠져 있었는데, 이번에 빌드하면서 문자열이 자동 추출되어 카탈로그에 등록됐습니다.

**항목만 등록됐고 en/ja 번역은 비어 있습니다.** 지금 상태로는 영어·일본어 사용자에게 한국어가 그대로 노출됩니다.

이번 iCloud 작업으로 번역이 필요해진 문자열 **5개**:

| 문자열 | 위치 |
|---|---|
| `iCloud와 동기화하시겠습니까?` | `ICloudOnboardingAlertView.swift` |
| `iCloud 사용` | `ICloudOnboardingAlertView.swift`, `ICloudSettingView.swift` |
| `iCloud 설정` | `SettingView.swift`, `ICloudSettingView.swift` |
| `iCloud를 끄면 이 기기에서만 데이터가 저장됩니다` | `ICloudSettingView.swift` |
| `끄기` | `ICloudSettingView.swift` |

> ⚠️ **6장의 디자인 작업이 끝나면 문자열이 더 늘어납니다.**
> 실패 안내 문구(미로그인 / 용량 부족 / 네트워크 없음), 다운로드 상태, 진행률 표시 등이
> 아직 정해지지 않았습니다. **디자인 확정 후 한 번에 번역하는 편이 효율적입니다.**

참고로 카탈로그에는 번역이 비어 있는 항목이 총 17개인데, 나머지 12개
(`두 단`, `집중모드를 활성화 중입니다`, `다시 보지 않기` 등)는 이번 작업과 무관하게 원래부터 비어 있던 것들입니다.

### 참고: `Localizable.xcstrings`는 빌드할 때 자동으로 바뀝니다

Xcode가 빌드하면서 Swift 코드의 문자열을 추출해 이 파일에 추가합니다.
그래서 코드에 새 문자열을 넣고 빌드하면 **의도하지 않아도 이 파일이 변경 상태로 뜹니다.**
`git status`에 자꾸 올라온다면 대부분 이 경우이니, 확인 후 함께 커밋하면 됩니다.

### 참고: `NSUbiquitousContainers`의 함정

이 키는 **컨테이너에 파일이 처음 올라갈 때 한 번만** 서버에 반영됩니다. 이미 테스트하면서 컨테이너를 써본 기기가 있다면 설정이 적용되지 않은 채로 굳어 있으니, `CURRENT_PROJECT_VERSION`을 올려 다시 설치해야 합니다. 실사용자에게는 아직 출시 전이라 영향 없습니다.

### 참고: `NetworkUnitTest` 스킴이 없습니다

CLAUDE.md에는 테스트 실행 방법이 적혀 있지만, 프로젝트에 해당 스킴이 존재하지 않아 실행하지 못했습니다(공유 설정이 빠졌거나 제거된 듯). 이번 작업으로 생긴 문제는 아닙니다.
